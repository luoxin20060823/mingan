# 系统工作流程与优化前后对比

本文档介绍当前内容安全审核系统的完整工作流程，并对比第一次要求优化前的系统流程和当前流程之间的差异。

## 一、当前系统总体流程

当前系统采用多层审核架构，核心流程如下：

```text
用户输入文本
  -> API 接收请求
  -> 读取词库、正则规则、策略配置
  -> L1 词库与正则命中
  -> L2 变体识别
  -> L3 语义审核
  -> L4 融合决策
  -> 处置建议生成
  -> 保存审核记录
  -> 返回前端结果
```

系统不是单纯依赖关键词，而是将规则、变体识别、语义模型、本地兜底和风险融合结合起来。

## 二、当前各模块职责

### 1. API 接入层

主要接口：

- `/audit/text`：单条文本审核；
- `/audit/batch`：批量文本审核；
- `/words`：敏感词管理；
- `/rules`：正则规则管理；
- `/policy`：策略阈值管理；
- `/history`：审核历史记录。

单条审核适合前端实时使用，批量审核适合评测和批处理任务。

### 2. L1 词库与正则层

L1 使用敏感词库、Aho-Corasick 自动机和正则规则进行快速扫描。

当前能力：

- 支持内置词库和用户自定义词；
- 支持 URL、站外引流、联系方式等正则规则；
- 支持低质量词过滤，减少误命中；
- 对自定义词打上 `custom_word` 标记，避免后续被误降权。

### 3. L2 变体识别层

L2 用于识别绕过式表达，包括：

- 空格拆分；
- 符号插入；
- 拼音变体；
- 谐音映射；
- 字形混淆。

当前优化点：

- 拼音变体在引擎初始化时预计算；
- 扫描时复用预计算结果，减少大词库下的重复计算；
- 对技术标识符等场景做了误判保护。

### 4. L3 语义审核层

L3 是系统的语义判断层，分为两种模式：

```text
有 DEEPSEEK_API_KEY -> 调用外部语义模型 + 本地语义兜底
无 DEEPSEEK_API_KEY -> 仅使用本地语义兜底
```

当前 L3 能力：

- 要求外部模型返回结构化 JSON；
- 支持 `合规`、`提示`、`警告`、`违规` 四级风险；
- 支持 `涉政`、`暴恐`、`色情`、`辱骂`、`违法广告`、`诈骗`、`引流`、`未成年人风险`、`低俗`、`其他` 等分类；
- 本地兜底覆盖诈骗、引流、未成年人风险、博彩、黑产广告等典型高信号场景；
- 当本地高置信结果强于外部模型弱判定时，可以采用本地结果。

### 5. L4 融合决策层

L4 将 L1、L2、L3 的分数和分类融合成最终结论。

当前逻辑：

- 取多层风险分数中的最高风险作为主要依据；
- 根据策略阈值映射为 `合规`、`提示`、`警告`、`违规`；
- 优先保留更具体的风险分类；
- 当 L3 判定合规时，对 L1/L2 中上下文性、非特异性告警进行降权；
- 不对用户自定义词进行误降权。

### 6. 处置建议层

系统会根据最终风险等级和分类生成平台动作：

| 风险等级 | 常见动作 |
| --- | --- |
| 合规 | pass |
| 提示 | hint 或 pass |
| 警告 | fold 或 manual_review |
| 违规 | delete 或 block |

高风险类别，如未成年人风险、诈骗、暴恐等，会更倾向于拦截或人工复核。

### 7. 记录与评测层

系统会保存审核结果，包括：

- 风险等级；
- 分类；
- 置信分；
- L1/L2/L3 分数；
- 命中明细；
- LLM 解释；
- 处置建议；
- 各层耗时。

评测脚本现在使用 `/audit/batch`，能够批量复用审核器，适合跑真实数据集评测。

## 三、第一次优化前的系统流程

第一次要求优化前，系统已经具备基础审核链路，但存在明显问题：

```text
输入文本
  -> L1 词库命中
  -> L2 变体识别
  -> L3 语义判断
  -> L4 简单融合
  -> 生成处置建议
```

主要不足：

- 真实词库质量不够稳定，部分词容易造成误判；
- 技术日志、正常讨论中出现敏感词时，容易被抬高风险；
- L3 判断为合规时，L1/L2 的弱命中仍可能导致最终拦截；
- 本地语义兜底覆盖范围有限，对黑产短句、博彩短句识别不足；
- 外部模型弱判定时，本地高置信规则不能有效接管；
- 评测脚本逐条调用 `/audit/text`，大样本评测很慢；
- 文档和评测体系不够清晰，线上语义层、本地模式、演示评测容易混在一起。

## 四、当前流程相比优化前的变化

| 对比项 | 优化前 | 当前系统 |
| --- | --- | --- |
| 词库命中 | 直接影响最终风险，误判较多 | 增加低质量词过滤和上下文保护 |
| 自定义词 | 与普通词类似处理 | 增加 `custom_word` 标记，保留用户策略权重 |
| L2 变体识别 | 每次扫描重复计算拼音 | 初始化预计算，性能更稳 |
| L3 语义层 | 外部模型或本地兜底，覆盖较弱 | 外部模型 + 本地高信号兜底，且支持本地覆盖弱判定 |
| 黑产短句 | `抄小说吗`、`dy评论` 等容易漏判 | 增加短广告/黑话组合规则 |
| 正常讨论 | 容易因敏感词被拦截 | L3 合规时可对上下文告警降权 |
| 融合决策 | 更偏最高分硬融合 | 增加上下文调节和分类优先级 |
| 处置动作 | 可能出现描述合规但动作拦截不一致 | 融合逻辑更一致，降低误处置 |
| 评测脚本 | 逐条请求，速度慢 | 使用 `/audit/batch` 批量评测 |
| 文档体系 | 说明分散 | 增加真实评测、线上语义评测、演示评测、流程对比文档 |

## 五、当前系统现状

当前系统已经具备课程设计和原型演示所需的完整链路：

- 支持前端审核界面；
- 支持敏感词、正则规则、策略配置管理；
- 支持单条和批量审核；
- 支持线上语义层和本地模式两种运行方式；
- 支持真实数据集评测；
- 支持演示友好评测；
- 已有单元测试、集成测试和性能测试。

从效果看：

- 线上语义层 280 样本 F1 为 `0.6913`；
- 本地模式 420 样本 F1 为 `0.4078`；
- 演示友好 20 样本 F1 为 `0.9474`。

这说明系统在清晰违规场景下表现较好；在复杂真实语义场景下仍有明显提升空间。

## 六、当前主要优势

- **链路完整**：从输入、审核、融合、处置到记录闭环完整。
- **可解释性较好**：返回 L1/L2/L3 分数、命中明细和语义解释。
- **可配置性较强**：支持词库、正则、策略阈值调整。
- **误判控制更稳**：正常技术记录和反诈科普不再容易被直接拦截。
- **演示效果好**：演示友好评测准确率达到 `95.00%`。

## 七、当前主要不足

- 复杂真实场景召回率仍偏低；
- 隐晦辱骂、性别歧视、软诈骗识别不足；
- 黑话词库仍需要持续扩充；
- 部分分类仍会漂移；
- 线上语义层依赖外部 API、网络、费用和模型稳定性。

## 八、后续优化方向

建议后续优先做以下工作：

1. 增加专门的辱骂、歧视、软诈骗语义分类器；
2. 继续扩充黑产广告和博彩黑话样本；
3. 为不同类别设置独立阈值，而不是完全共用全局阈值；
4. 增加人工复核队列，用于处理不确定内容；
5. 将线上语义模型的提示词和分类标准进一步结构化；
6. 建立固定回归样本集，每次修改后自动跑指标对比。

## 九、总结

优化前，系统已经能完成基础敏感词审核，但容易误判正常内容，也容易漏掉短广告和隐晦风险。当前系统已经发展为多层融合审核架构，具备更好的可解释性、可配置性、测试能力和演示效果。

不过，当前系统仍更适合作为课程设计、原型系统或人工审核辅助工具。若要达到更强商用效果，还需要继续增强语义模型能力和复杂场景召回能力。
